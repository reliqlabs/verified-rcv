## Headline

The v0.3.9 commit substantially closes the two residual Criticals from the prior re-audit. **C2 residual (B8 (a)/(b)/(d) unimplemented)** is now fully closed: the contract directly calls `/xion.zk.v1.Query/ProofVerifyGnark` with the gnark proof, byte-extracts measurements from `public_inputs`, compares them to the registry, and verifies the `ReportData` half-and-half layout (commit hash + DST tag). **N2 (admin pubkey substitution)** is **narrowed** by a new B8(e) clause: `CreateElection` now requires a registration TDX quote whose `ReportData[0..32] = SHA-256(enclave_pubkey)` and whose measurements match the registry, so admin can no longer pick an arbitrary pubkey. Residual concern flagged below: the registration quote has no freshness binding (no contract_addr, election_id, chain_id, or nonce in its preimage), so a leaked-then-recovered enclave privkey could be re-attested by replaying a stale registration quote.

The rewrite is otherwise disciplined: 39 new contract tests cover every rejection path, 18 runtime tests cover the synthetic public_inputs builders, and 7 cross-tests assert byte-equality between the contract's and runtime's `canonical_serialization` / `build_report_data` / extraction functions.

Three significant issues introduced by the rewrite:

1. **Spec/code drift on N4** (chain_id). The code added `chain_id` to `canonical_serialization` and `compute_commit_hash`, but the commit message claims N4 is "Out of scope (remediation tracked separately)," the intent.md is at v0.3.9, and the code's doc-comments reference "v0.3.10" — a version that does not exist in `intent.md`'s history. The change is real; the documentation does not match.
2. **`cargo clippy --all-targets` exit-nonzero** due to a `clippy::erasing_op` denied-by-default lint at `attestation.rs:387` (`pi[0 * 32 + 31]` always evaluates as `pi[31]`). A CI gate that runs `clippy --all-targets` would fail today.
3. **No working production attestation path**. The runtime's `produce_artifacts_inner` under `--features real-zkdcap` returns `Err("real-zkdcap path not yet wired")` — a hard stub. Without `real-zkdcap`, the runtime emits a 192-byte sentinel proof that the chain's `ProofVerifyGnark` will reject (any non-mock build). The chain is now fully attestation-gated, but no client can yet produce an attestation the chain will accept end-to-end. This is acknowledged in the commit message's "out of scope" list but worth flagging as a blocker for testnet/mainnet deployment.

These three are tractable next-cycle items. The Critical and Major exploit paths from the prior cycle are closed.

## Closure status

### Critical (residual prior — C2/N1 + N2 cluster)

#### Prior C2 / N1: chain-side B8 (a)/(b)/(d) verification — **closed**

The contract now performs all four B8 clauses:

| B8 clause | Status at db2021c | Code reference |
|---|---|---|
| (a) TDX quote validity | Closed via gnark proof verification | `contract.rs:721-754` `verify_gnark_proof_via_xion` calls `/xion.zk.v1.Query/ProofVerifyGnark` |
| (b) Groth16 zkdcap proof | Closed via the same | same |

| (d) MRTD/RTMR vs registry | Closed via measurement extraction + bytewise compare | `contract.rs:646-675` `verify_measurements_match_registry` |

The `EnclaveImageRegistry` schema was updated: `vkey: Vec<u8>` → `vkey_name: String` (the actual vkey content lives in Xion's `xion.zk` store; the contract holds only the name reference); split `rtmr` into mandatory `rtmr1`, `rtmr2` and optional `rtmr0`, `rtmr3`; new `accepted_tcb_statuses: Vec<u8>` for operator-configurable TCB policy.

A new `verify_publish_quote` and `verify_registration_quote` pair sequence the steps:

1. `validate_public_inputs_shape(pi)` — must be 9_792 bytes (306 fr-elements × 32).
2. `verify_measurements_match_registry(pi, registry)` — extract MrTd, Rtmr1, Rtmr2 (always); Rtmr0, Rtmr3 if `Some` in registry. Bytewise compare.
3. `verify_tcb_status_accepted(pi, registry)` — extract u64, check ≤ 5 (6=Revoked is circuit-hard-rejected by gnark; chain hard-rejects > 6 as out-of-range), check membership in `registry.accepted_tcb_statuses`.
4. `extract_report_data(pi)` — 64 bytes; `rd[..32]` must equal either the commit hash (publish quote) or `SHA-256(enclave_pubkey)` (registration quote); `rd[32..64]` must equal the zero-padded purpose-tagged DST (`DST_VERIFIED_RCV_TALLY_V1` vs `DST_VERIFIED_RCV_PUBKEY_V1`).
5. `verify_gnark_proof_via_xion(deps, proof, pi, &registry.vkey_name)` — the actual `xion.zk` gRPC verify.

The `uints.U8` invariant (high 31 bytes of each 32-byte BE fr-element must be zero) is enforced per-element by `extract_u8_from_fr` at `contract.rs:587-594`. Out-of-range u64 (TcbStatus / Timestamp with non-zero high 24 bytes) is rejected at `extract_u64_from_fr:598-607`.

Negative tests at `contract.rs::tests` cover: `gnark_public_inputs_length`, `u8_high_byte_nonzero_rejected`, `u8_low_byte_extracted_correctly`, `publish_quote_wrong_length_rejected`, `publish_quote_wrong_domain_tag_rejected` (`AttestationDomainTagInvalid`), `publish_quote_wrong_commit_hash_rejected` (`AttestationCommitMismatch`), `publish_quote_wrong_contract_addr_rejected`, `publish_quote_wrong_measurements_rejected` (per-field `mrtd`/`rtmr1`/`rtmr2`/`rtmr0`/`rtmr3` plus optional-slot unbound-skip), `tcb_status_accept_reject`, `registration_quote_wrong_dst_rejected` (cross-purpose: registration ≠ publish DST), `publish_quote_correct_binding_ok`, and `create_election_with_bad_registration_quote_rejected`. 39 contract tests in total; all pass.

#### Prior N2: admin pubkey substitution — **narrowed** (residual: registration quote replay)

`CreateElection` at `contract.rs:231-318` now requires `proof` and `public_inputs` arguments. Before storing the `enclave_pubkey`, it calls `verify_registration_quote(deps.as_ref(), &registry, &enclave_pubkey, &proof, &public_inputs)`. This verifies a TDX quote (via gnark) whose `ReportData[0..32] = SHA-256(enclave_pubkey)` and whose measurements equal the registered values. The admin can no longer pick an arbitrary pubkey — the pubkey must come from a TDX enclave whose code measures to the registered MRTD/RTMR.

Combined with the chain Trust assumption that Xion's `xion.zk` module correctly verifies Groth16 proofs against the registered vkey, and the operational assumption that dstack KMS releases the per-election privkey only to the matching attested enclave, the admin substitution attack is **cryptographically blocked**.

**Residual**: the registration `ReportData` preimage is `SHA-256(enclave_pubkey)` — that is, only the pubkey itself. No contract_addr, election_id, chain_id, timestamp, or chain-state nonce is included. Consequence:

- A single valid registration quote can be reused across multiple `CreateElection` calls (same contract, even on a fork or a re-instantiated contract address).
- If at some later time the enclave's privkey is exfiltrated by an attacker (e.g., a side-channel against TDX, a dstack KMS misbehavior), the attacker can capture an old registration quote and use it to launch a new election whose ballots they can decrypt. There is no on-chain freshness signal proving the privkey is still in the enclave's possession.

This is tracked as new finding **N15** below. Severity: Minor-to-Major depending on the dstack KMS lifecycle assumptions.

### Finding N7: Code added `chain_id` to `canonical_serialization` while commit message claims N4 is out-of-scope; doc-comments reference a "v0.3.10" that does not exist in intent.md

**Severity:** Minor
**Confidence:** 95/100
**Principle Violated:** VCL-STMT-006 (cross-document interface mismatch — between commit message, code doc-comments, and the intent document)
**Location:** `contract.rs:847-859` (`canonical_serialization`), `attestation.rs:67-82` (mirror), commit message body, `.colosseum/intent.md` v0.3.9 section

#### Description

The `compute_commit_hash` and `canonical_serialization` functions were extended at db2021c to take a `chain_id: &str` argument between `contract_addr` and `election_id`. The change is mirrored across:

- `contract.rs:831-859` (the chain-side encoder)
- `attestation.rs:70-82` (the runtime mirror)
- `cross_canonical.rs:38-66` (the cross-test, including a `chain_id_affects_canonical_serialization_bytes` test that explicitly asserts the new field)
- The `TallyRequest` proto at `proto/tally.proto:33-37` (new `chain_id = 5` field)
- The `exec_publish_result` handler at `contract.rs:385` reads `env.block.chain_id` at PublishResult time and threads it through.

The doc-comment at `contract.rs:827-830` reads:

> Compute the canonical commit hash per intent §2.5 (v0.3.10 form): `SHA-256(canonical_serialization(contract_addr ‖ chain_id ‖ election_id ‖ tally_body))`. Pinned at v0.3.9 to bind ReportData[0..32] of the publish quote; `chain_id` added at v0.3.10 (N4) for cross-chain replay defense.

The intent.md document is at version **0.3.9**. Its v0.3.9 revision-history entry explicitly defines the commit hash preimage as `SHA-256(canonical_serialization(contract_addr ‖ election_id ‖ tally_body))` — no `chain_id`. The history has no v0.3.10 entry.

The commit message lists N4 explicitly:

> Out of scope (remediation tracked separately):
> - N4: chain_id in canonical_serialization.

Three pieces of documentation now disagree:

1. The intent document says the commit hash binds `(contract_addr, election_id, tally_body)`.
2. The commit message says N4 is out of scope.
3. The code (and its doc-comments) says the commit hash binds `(contract_addr, chain_id, election_id, tally_body)`.

#### Exploit Path

Not exploitable in a security sense. The risk is methodology-process: the intent document is supposed to be the trust anchor that downstream Lean / Quint specs refine. With the code ahead of the intent by an undocumented version bump, downstream artifacts (Lean math spec, Quint protocol model, ledger) may continue to verify against the v0.3.9 statement that no longer matches the code. A reader who consults the intent gets a different specification than the code implements.

A concrete consequence: the v0.3.9 entry's stated commit-hash formula is now wrong relative to the deployed contract. A second auditor reading only the intent would conclude the chain accepts a different commit binding than it actually does.

#### Recommended Fix

Two options. Either:

**A (preferred)**: bump intent to v0.3.10. Add a `- v0.3.10 — 2026-05-26 PATCH: ...` entry documenting the `chain_id` addition and its placement in the canonical serialization. Update §3.2 B8(c) to read `... SHA-256(canonical_serialization(contract_addr ‖ chain_id ‖ election_id ‖ tally_body))`. Update §2.5's canonical-serialization paragraph. Update `.colosseum/ledger.md` if it references the prior formula.

**B**: revert the code. Remove `chain_id` from `canonical_serialization`. Re-revert if/when an intent v0.3.10 lands.

Option A is the obvious choice — the change is good (cross-chain replay defense per the original Lead L9 / Finding N4). The intent should catch up to the code.

### Finding N8: `cargo clippy --workspace --all-targets` fails at db2021c due to `clippy::erasing_op` deny-by-default

**Severity:** Minor
**Confidence:** 100/100
**Principle Violated:** deployment hygiene (a CI gate that runs `--all-targets` would fail)
**Location:** `crates/enclave/src/attestation.rs:387`

#### Description

In the test `public_inputs_u8_invariant` at line 372, the assertion `assert_eq!(pi[0 * 32 + 31], 0xAB)` uses `0 * 32 + 31` for readability symmetry with the next line `assert_eq!(pi[47 * 32 + 31], 0xCD)`. Clippy's `erasing_op` lint (denied by default — i.e., it is an error, not a warning) flags this because `0 * 32` always evaluates to zero. The compilation fails:

```
error: this operation will always return zero. This is likely not the intended outcome
   --> crates/enclave/src/attestation.rs:387:23
    |
387 |         assert_eq!(pi[0 * 32 + 31], 0xAB);
    |                       ^^^^^^
```

`cargo test -p verified-rcv-enclave --lib` does not surface this error because it doesn't run clippy. But any CI step that includes `cargo clippy --workspace --all-targets` fails today.

The prior re-audit's recommended Finding N5 fix (add `cargo clippy --workspace --all-targets -- -D warnings` to CI) would catch this immediately. The fact that the v0.3.9 rewrite landed without that gate means the regression was not caught at commit time.

#### Recommended Fix

```rust
// crates/enclave/src/attestation.rs:387
assert_eq!(pi[31], 0xAB);              // was: pi[0 * 32 + 31]
assert_eq!(pi[47 * 32 + 31], 0xCD);
```

Either drop the `0 * 32 +` prefix (the elegant fix) or add `#[allow(clippy::erasing_op)]` to the test (the documenting fix). The elegant fix is preferred — it does not lose any readability since the symmetry is obvious from the second line.

A complementary fix is to add the clippy gate to CI per prior Finding N5. The v0.3.9 commit-message lists N5 as out-of-scope; this finding is evidence that N5 should be raised in priority.

### Finding N10: Test-time coverage gap: `verify_gnark_proof_via_xion` is no-op'd under `#[cfg(test)]`; prost encoding / decoding paths are unexercised

**Severity:** Minor
**Confidence:** 80/100
**Principle Violated:** test-coverage discipline (a runtime-only code path is untested)
**Location:** `contract.rs:721-766`

#### Description

The function `verify_gnark_proof_via_xion` has two implementations, gated by:

```rust
#[cfg(not(any(feature = "mock-attestation", test)))]
fn verify_gnark_proof_via_xion(...) -> Result<(), ContractError> {
    let req = QueryVerifyGnarkRequest { ... };
    let mut req_bytes = Vec::new();
    req.encode(&mut req_bytes)?;
    let resp_bin: Binary = deps.querier.query(&QueryRequest::Grpc(GrpcQuery {
        path: "/xion.zk.v1.Query/ProofVerifyGnark".to_string(),
        data: Binary::from(req_bytes),
    }))?;
    let resp = ProofVerifyGnarkResponse::decode(resp_bin.as_slice())?;
    if !resp.verified { return Err(ContractError::ProofVerificationFailed); }
    Ok(())
}

#[cfg(any(feature = "mock-attestation", test))]
fn verify_gnark_proof_via_xion(...) -> Result<(), ContractError> { Ok(()) }
```

Under `cfg(test)`, the function is replaced by a no-op `Ok(())`. The test suite exercises every other rejection path (length, U8 invariant, u64 range, measurements, ReportData, DST tag, commit hash, pubkey binding), but does NOT exercise:

- prost-encoding of `QueryVerifyGnarkRequest`. A regression in field tags, types, or wire format would not be caught.
- prost-decoding of `ProofVerifyGnarkResponse`. Same concern.
- The exact path string `"/xion.zk.v1.Query/ProofVerifyGnark"` and its match against Xion's actual gRPC routing.
- The `GrpcQuery` request/response shape against `cosmwasm-std`'s actual `QueryRequest::Grpc` variant.
- Failure-path: what happens when the gRPC call itself errors (network, missing module, malformed response).

A production wasm with broken prost-encoding would fail at runtime against the real Xion chain, with no test-time signal.

#### Recommended Fix

Add a **byte-level prost goldenfile test** that constructs a known `QueryVerifyGnarkRequest`, encodes it, and compares the bytes to a hex fixture. Likewise for the response decoder. This is independent of whether the chain itself is reachable; it just pins the wire format:

```rust
#[test]
fn query_verify_gnark_request_encoding_matches_proto() {
    let req = QueryVerifyGnarkRequest {
        proof: vec![0x01, 0x02],
        public_inputs: vec![0x03, 0x04],
        vkey_name: "test".into(),
        vkey_id: 0,
    };
    let mut buf = Vec::new();
    req.encode(&mut buf).unwrap();
    // Expected bytes — derived once by hand against Xion's proto spec and pinned here.
    let expected_hex = "...";
    assert_eq!(hex::encode(&buf), expected_hex);
}
```

The fixture would be regenerated only when Xion's proto schema changes (a deliberate event).

### Finding N11: `--features real-zkdcap` is a stub that always errors; no working end-to-end production attestation path exists at db2021c

**Severity:** Minor
**Confidence:** 95/100
**Principle Violated:** deployment readiness (the chain rejects everything the runtime can currently emit, in a non-`mock-attestation` build)
**Location:** `crates/enclave/src/attestation.rs:297-309`

#### Description

The runtime crate has two compile-time paths for producing a publish or registration attestation:

```rust
#[cfg(not(feature = "real-zkdcap"))]
async fn produce_artifacts_inner(...) -> Result<(Vec<u8>, Vec<u8>), AttestationError> {
    // Synthesize public_inputs from the (mock) identity, return a 192-byte
    // sentinel proof. The chain's mock-attestation feature skips the
    // ProofVerifyGnark gRPC call entirely.
    let public_inputs = build_public_inputs(...);
    let proof = vec![0xABu8; 192];
    Ok((proof, public_inputs))
}

#[cfg(feature = "real-zkdcap")]
async fn produce_artifacts_inner(...) -> Result<(Vec<u8>, Vec<u8>), AttestationError> {
    // TODO(real-zkdcap): connect to zkdcap gnark prove server via unix socket
    // ...
    Err(AttestationError::ZkProver("real-zkdcap path not yet wired; ...".into()))
}
```

Consequences:

- **`cargo build` (default features)**: runtime emits a sentinel proof. Contract built without `mock-attestation` will reject this when `ProofVerifyGnark` returns `verified=false` (the sentinel is not a valid Groth16 proof for any vkey). End-to-end tally cannot complete.
- **`cargo build --features real-zkdcap`**: the runtime fails at the artifact-production step with `Err`. End-to-end tally cannot complete.
- **`cargo build` on the runtime + `cargo build --features mock-attestation` on the contract**: end-to-end works but the chain skips proof verification — the tally is finalized without any cryptographic anchor.

In other words, there is no compile-time combination that produces a chain-acceptable real attestation. The chain's verification is now cryptographically tight, but no client can currently generate input that satisfies it without the mock-attestation gate also being on.

This is a methodology-Ask-Z item: "deferred is panic" / "stub-as-Ok is forbidden." The current `real-zkdcap` stub at least returns `Err` rather than `Ok(())` (good), but the project has no other path to a real attestation.

#### Recommended Fix

Either:

**A**: implement `produce_artifacts_inner` under `feature = "real-zkdcap"` by wiring the zkdcap Go gnark prove server per the docstring's TODO. The commit message references `/Users/mvid/Development/reliq/zkdcap/host/src/gnark.rs` as the reference; the integration is a unix-socket POST with the quote + a witness JSON. This is the proper closure.

**B**: temporarily allow a documented "test-but-chain-accepting" mode where the contract holds a `dev_vkey_name` in the registry that maps (via `xion.zk`) to a vkey whose proof-of-knowledge requires only knowledge of the sentinel structure. This is fragile and not recommended; documented here only because the option exists.

The recommended path is **A**. Until it lands, the system can be exercised end-to-end only via `mock-attestation`, and the chain side's gnark verifier is dormant.

### Finding N12: `verify_gnark_proof_via_xion` populates both `vkey_name` and `vkey_id`; the Xion API's lookup behavior under this combination should be verified

**Severity:** Lead (insufficient evidence to confirm severity)
**Confidence:** 50/100
**Principle Violated:** N/A; potential cross-contract interface mismatch (VCL-STMT-006)
**Location:** `contract.rs:728-733`

#### Description

The `QueryVerifyGnarkRequest` prost message has four fields:

```rust
#[derive(Clone, PartialEq, prost::Message)]
struct QueryVerifyGnarkRequest {
    #[prost(bytes = "vec", tag = "1")] proof: Vec<u8>,
    #[prost(bytes = "vec", tag = "2")] public_inputs: Vec<u8>,
    #[prost(string, tag = "3")]        vkey_name: String,
    #[prost(uint64, tag = "4")]        vkey_id: u64,
}
```

The contract populates `vkey_name` from the registry and sets `vkey_id: 0`. The intended semantics depend on Xion's `xion.zk.v1.Query/ProofVerifyGnark` implementation:

- If Xion uses `vkey_name` as the primary lookup and ignores `vkey_id` when 0, the current code is correct.
- If Xion uses `vkey_id` as the primary lookup and `vkey_name` only as a fallback or sanity check, the current code may silently lookup an unintended vkey (id 0 may correspond to a placeholder, the first registered vkey, or an error case).
- If Xion requires both to match (vkey_name AND vkey_id), the current code may always fail with "vkey_name does not match vkey_id 0".

The comment references `/Users/mvid/Development/burnt/xion/proto/xion/zk/v1/query.proto` as the proto source. Without reading that file (it is in a separate repository), the lookup semantics cannot be verified from this audit.

#### Recommended Investigation

Read the Xion proto and the corresponding keeper implementation in the `xion.zk` module. Determine the lookup behavior with `vkey_name=non-empty, vkey_id=0`. Either:

- Document the chosen semantic in the contract's doc-comment.
- Add a Stargate-level integration test against a local Xion chain that exercises a real `ProofVerifyGnark` call with a known vkey_name and vkey_id=0; confirm `verified=true` for a real proof.

If Xion requires `vkey_id` to be the registered id, the registry schema should include `vkey_id: u64` alongside (or instead of) `vkey_name`, and the validation logic at instantiate should accept it.

**Location:** `contract.rs:796-821` (`verify_registration_quote`); `attestation.rs:159-167` (`build_registration_report_data`)

#### Description

The registration `ReportData[0..32]` is computed as `SHA-256(enclave_pubkey)`. The preimage is **only the pubkey** — no contract_addr, no election_id, no chain_id, no timestamp, no nonce, no chain-state binding.

Compare to the publish quote, whose `ReportData[0..32]` is `SHA-256(canonical_serialization(contract_addr ‖ chain_id ‖ election_id ‖ tally_body))` — the publish quote is one-shot, bound to a specific election and tally.

Consequence: a single valid registration quote works forever and for any `CreateElection` invocation. Concrete scenario:

1. Operator runs a legitimate verified-rcv enclave at time T0. The enclave produces a valid `(proof, public_inputs)` for `enclave_pubkey_T0`. The admin uses these to call `CreateElection_1`.
2. Time passes. The election runs to completion. dstack KMS does its lifecycle (key released to enclave at attestation, presumed deleted after).
3. At time T2, the operator (or any party with the registration quote bytes from chain history) calls `CreateElection_2` re-submitting the same `(enclave_pubkey_T0, proof, public_inputs)`. The chain verifies the gnark proof again (it still verifies), the measurements still match the registry, ReportData binds the same pubkey. The chain accepts.
4. If between T0 and T2 the enclave's privkey was leaked (TDX side-channel; dstack KMS misconfiguration; insider exfil), the attacker can decrypt every ballot submitted under election_2.

The strength of this attack depends on the dstack KMS lifecycle. The intent at §6.3 names `dstack_kms_trust` as the operational assumption that the privkey is released only to the matching attested enclave and not retained outside it. If that assumption fails at any later time, the lack of freshness binding in the registration quote means there is no on-chain recourse.

#### Recommended Fix

Include freshness in the registration `ReportData` preimage. Concretely:

```rust
// attestation.rs::build_registration_report_data — new signature
pub fn build_registration_report_data(
    enclave_pubkey: &[u8],
    contract_addr: &str,
    chain_id: &str,
    expected_election_id: u64,  // the next election_id the admin will create
) -> [u8; 64] {
    let mut hasher = Sha256::new();
    hasher.update(enclave_pubkey);
    hasher.update(contract_addr.as_bytes());
    hasher.update(chain_id.as_bytes());
    hasher.update(&expected_election_id.to_le_bytes());
    let h = hasher.finalize();
    let mut rd = [0u8; 64];
    rd[..32].copy_from_slice(&h);
    rd[32..32 + DST_PUBKEY.len()].copy_from_slice(DST_PUBKEY);
    rd
}
```

And the chain-side `verify_registration_quote` recomputes the same hash, reading `contract_addr` from `env.contract.address`, `chain_id` from `env.block.chain_id`, and `expected_election_id` from `ELECTION_COUNTER + 1` (the id the new election will receive).

This makes each registration quote one-shot, bound to a specific (chain, contract, election_id) triple. A leaked-privkey replay would require the attacker to convince the legitimate enclave to produce a registration quote for the NEW election_id — which requires the enclave to be alive and well-behaved at that time.

This is the analogous defense the publish quote already has (intent §3.2 B8(c) via canonical_serialization). Applying it symmetrically closes the registration replay.

### Finding N14: `chain_id` is the rightmost defense layer for cross-chain replay, but `env.block.chain_id` semantics on Xion should be confirmed

**Severity:** Lead
**Confidence:** 55/100
**Principle Violated:** N/A
**Location:** `contract.rs:385` (`exec_publish_result` reads `env.block.chain_id`)

#### Description

The N4 closure includes `chain_id` in the canonical-serialization preimage. The contract reads it from `env.block.chain_id.as_str()` at `PublishResult` time. The runtime takes `chain_id` as a `TallyRequest` proto field from the orchestrator. If the orchestrator passes a different `chain_id` than what the chain actually has at PublishResult time (e.g., a misconfigured environment variable), the chain will compute a different commit hash than the enclave used to build `ReportData`, and the verification will fail with `AttestationCommitMismatch`.

This is fail-safe for cross-chain replay (an enclave attestation for chain A cannot be replayed on chain B because the commit hash differs). But it relies on the operator setting the orchestrator's `chain_id` equal to the chain's actual `env.block.chain_id`. A subtle deployment error here results in a `AttestationCommitMismatch` rejection at every PublishResult attempt.

Two minor concerns:

1. **`env.block.chain_id` stability**: on most Cosmos SDK chains, `chain_id` is a chain-level constant (`xion-1`, `xion-testnet-1`, etc.) and does not change. CosmWasm exposes it via `env.block.chain_id`. If a chain upgrade (e.g., a hard fork that bumps the chain_id) ever occurs, every `enclave_pubkey` registered under the old chain_id would be unrecoverable for a new election (the registration quote would fail commit comparison — wait, no, the registration ReportData does NOT include chain_id per N13's current code). So chain-id-bumping forks only break publish, not registration. Worth documenting.

2. **Smoke test fixture mismatch**: `crates/enclave/src/bin/smoke.rs:38` defaults `chain_id` to `"xion-smoke-1"`. A smoke test that sends this against a real testnet contract (whose `env.block.chain_id` is `xion-testnet-2` or similar) will fail. This is fine — it's a smoke test against a smoke deployment — but the default should match the most common usage to reduce operator confusion.

#### Recommended Investigation

Confirm Xion's `chain_id` strings for testnet and mainnet. Document them in `docs/deploy.md` and adjust the smoke test's default `chain_id` to a sensible value (or require it as a non-default flag). Optionally, add chain_id to the registration quote per Finding N13 to make the registration also chain-bound.

### Finding N15: `extract_u8_from_fr` and `extract_u64_from_fr` panic on out-of-bounds slice access; safety relies on prior `validate_public_inputs_shape` ordering

**Severity:** Informational (defensive-programming style)
**Confidence:** 90/100
**Principle Violated:** VCL-ERRH-002 (panics — though in CosmWasm the panic translates to tx abort, not chain halt)
**Location:** `contract.rs:587-607`

#### Description

```rust
pub fn extract_u8_from_fr(public_inputs: &[u8], elem_idx: usize) -> Result<u8, ContractError> {
    let start = elem_idx * FR_BYTES;
    let chunk = &public_inputs[start..start + FR_BYTES];  // PANIC if out-of-bounds
    if chunk[..31].iter().any(|&b| b != 0) {
        return Err(ContractError::GnarkPublicInputNotU8 { elem_idx });
    }
    Ok(chunk[31])
}
```

If `elem_idx >= 306` (or if `public_inputs.len() < (elem_idx + 1) * 32`), the slice index panics. In the call chain inside `verify_publish_quote` and `verify_registration_quote`, this is preceded by `validate_public_inputs_shape` which ensures `public_inputs.len() == 9_792`. All `extract_*` callers use elem_idx values bounded by constants (max is ELEM_TIMESTAMP = 305). So the live call graph is safe.

However:

1. The functions are `pub fn` — external code (library users, future maintainers, tests) could call them with arbitrary `elem_idx` and trigger a panic.
2. A future refactor that adds a new extraction path without prepending a length check would silently introduce panic potential.
3. CosmWasm semantics convert the panic to a transaction abort, so the impact is "tx is rejected with a non-descriptive error" rather than "chain halts." Still uglier than returning a structured error.

#### Recommended Fix

Add bounds checks inside the helpers (defensive programming) and make them not-`pub` if external callers don't need them:

```rust
pub(crate) fn extract_u8_from_fr(
    public_inputs: &[u8],
    elem_idx: usize,
) -> Result<u8, ContractError> {
    let start = elem_idx * FR_BYTES;
    let end = start + FR_BYTES;
    if end > public_inputs.len() {
        return Err(ContractError::GnarkPublicInputsLength {
            got: public_inputs.len(),
            expected: end,
        });
    }
    let chunk = &public_inputs[start..end];
    if chunk[..31].iter().any(|&b| b != 0) {
        return Err(ContractError::GnarkPublicInputNotU8 { elem_idx });
    }
    Ok(chunk[31])
}
```

The function is currently `pub` so that the runtime cross-test can call it (`cross_canonical.rs:144-149`). Leaving it `pub` is fine if the bounds check is added.

### Finding N16: `vkey_id: u64 = 0` is hardcoded in the gnark verify request; should be a registry field or documented as "always 0 in Xion's lookup model"
