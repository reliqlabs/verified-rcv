### v0.3.10's claimed N2 closure: examined in detail

The v0.3.10 commit replaces v0.3.8's immediate-rotation `UpdateRegistry` with a three-handler flow:

| Handler | Auth | Effect |
|---|---|---|
| `ProposeRegistryUpdate { registry }` | Admin only | Validates `registry`; rejects if any active election in Voting/Tallying; rejects if a pending update already exists; stores `PendingRegistry { registry, apply_after = now + delay }`. |
| `FinalizeRegistryUpdate {}` | **Permissionless** | Requires a pending update; requires `now >= pending.apply_after`; overwrites `REGISTRY`; clears `PENDING_REGISTRY`. |
| `CancelRegistryUpdate {}` | Admin only | Unconditionally removes `PENDING_REGISTRY`. |

Plus a new `Config.registry_update_delay_seconds: u64` and a new `QueryMsg::PendingRegistry` query for voter observability.

The trust-narrowing argument is real: an admin can no longer instantly swap to a registry pointing at an attacker-controlled enclave. The admin must propose, wait the timelock, finalize — with the pending value publicly observable. Voters who detect a malicious proposal can decline to vote in elections that begin after the proposal lands.

**But:** the chain does not prevent the admin from creating an election WHILE a registry update is pending. And `FinalizeRegistryUpdate` is permissionless with no phase check. This composition produces the timing attack documented as new finding **N17** below.

## New findings introduced by v0.3.10

### Finding N17: Permissionless `FinalizeRegistryUpdate` has no phase gate; finalize during Voting/Tallying of an election created after the propose bricks the election

**Severity:** Major (denial-of-service against in-flight elections)
**Confidence:** 90/100
**Principle Violated:** VCL-STMT-005 (state machine transition integrity); VCL-DDOS-001-equivalent (attacker can DoS an election cheaply)
**Location:** `crates/contract/src/contract.rs:469-482` (`exec_finalize_registry_update`); composition with `exec_create_election` at lines 261-274 and `exec_propose_registry_update` at lines 425-466

#### Description

The propose handler at `contract.rs:440-448` checks the current election's phase — it refuses to propose if the existing election is in Voting/Tallying. The create-election handler at `contract.rs:261-274` does NOT check whether a registry update is pending. The finalize handler at `contract.rs:469-482` checks ONLY the timelock; it does NOT check whether an election is in flight.

This composition yields an admissible sequence:

1. `t = 0`: previous election (if any) is in `Created` or `Resolved` (or no election). Admin calls `ProposeRegistryUpdate { registry: R2 }`. `apply_after = delay`.
2. `t = delay - ε`: admin calls `CreateElection`. New election with `start_at` slightly later. Phase becomes `Created`.
3. `t = delay`: voting opens. Phase becomes `Voting`. Voters submit ballots encrypted under the enclave_pubkey that was registration-quote-bound to the OLD registry `R1`.
4. `t = delay + ε`: any chain address calls `FinalizeRegistryUpdate`. The timelock check passes. `REGISTRY.save(deps.storage, &R2)`. No phase check.
5. End of voting window. Enclave produces a publish quote. The quote's `public_inputs` carry the enclave's measurements — which match `R1` (the enclave hasn't been swapped). The chain's `verify_publish_quote` calls `verify_measurements_match_registry(pi, &R2)`. Bytewise compare fails. Tally is rejected with `AttestationMeasurementMismatch { field: "mrtd" }` (or whichever measurement field differs first).
6. The election is stuck in Tallying. No publish can succeed under registry `R2` because no enclave with `R2`'s measurements is online (the legitimate enclave still has `R1`'s measurements). No party can revert to `R1` either, because `REGISTRY` was already overwritten by step 4.

Variants:

- **Naive operator path**: admin innocently proposes an upgrade then accidentally creates an election before the timelock expires; the election is bricked by the next `FinalizeRegistryUpdate` call. (Operational mistake, not malicious.)
- **Attacker DoS path**: anyone observing `PendingRegistry` (a public query) can time `FinalizeRegistryUpdate` to land at the first block after `apply_after`. If the admin already created an election whose Voting window straddles `apply_after`, the attacker bricks the election by paying only the gas of one tx. The attacker does not need to be admin and does not need access to any enclave.
- **Malicious admin path**: admin chains propose-then-create-election deliberately to construct a "stuck" election that can never publish. Tally never lands. Result obstructed.

Whether the registry change is meaningful or not, mid-election rotation breaks the publish path because the enclave's actual measurements no longer match what the chain expects. Even setting `R2 = R1` (identity update) would still pass — but a genuinely different `R2` is the realistic case (that's the point of the registry rotation feature).

#### Compensating Controls Checked

| Control | Status | Verdict |
|---|---|---|
| Phase check in `exec_propose_registry_update` | Present (rejects during Voting/Tallying of EXISTING election) | Doesn't cover the case where a new election is created AFTER the propose |
| Phase check in `exec_finalize_registry_update` | **Absent** | Vulnerable |
| Phase check in `exec_create_election` re pending updates | **Absent** | Vulnerable |
| Voter observability via `QueryMsg::PendingRegistry` | Present | Voters can SEE the pending update, but cannot themselves cancel or delay it; admin's `Cancel` is the only revert |
| `CancelRegistryUpdate` to abort the timing window | Admin-only | If the admin is the one creating the trap, they will not cancel |

#### Recommended Fix

Two viable approaches:

**A (cleaner)**: prevent the race entirely by refusing to create an election while a registry update is pending.

```rust
// crates/contract/src/contract.rs (inside exec_create_election, after admin auth)
if PENDING_REGISTRY.may_load(deps.storage)?.is_some() {
    return Err(ContractError::PendingRegistryUpdateBlocksNewElection);
}
```

This forces the admin to either `FinalizeRegistryUpdate` or `CancelRegistryUpdate` before they can create a new election. Voters then know that the moment a new election starts, the registry is settled and won't change mid-flight.

**B**: gate `exec_finalize_registry_update` on no-active-election.

```rust
// crates/contract/src/contract.rs (inside exec_finalize_registry_update, after timelock check)
if let Some(prev) = ELECTION.may_load(deps.storage)? {
    let phase = compute_phase(&env, &prev, deps.storage)?;
    if matches!(phase, Phase::Voting | Phase::Tallying) {
        return Err(ContractError::RegistryUpdateDuringActiveElection);
    }
}
```

This preserves the "permissionless finalize after timelock" property in the common case but adds the safety gate. Downside: it adds a new way for a malicious admin to indefinitely delay a finalize by keeping the contract in Voting (chain perpetual-Voting elections). The propose-handler's existing phase gate on the EXISTING election doesn't help once an election is created post-propose.

**A is preferred** because it makes the race impossible by construction: at any moment, either a registry update is pending OR an election is in flight, never both.

Add a negative test covering the race:

```rust
#[test]
fn finalize_during_voting_after_late_create_bricks_election() {
    // propose -> create election -> wait until in Voting and timelock expired ->
    // any caller can finalize -> publish then fails with measurement mismatch
}
```

Severity: Major because the attack is one-tx, requires no privilege, and is undetectable until the publish phase. The legitimate enclave wastes its work; voters' ballots are silently disenfranchised; admin has no recourse beyond redeploying the contract.

### Finding N18: `cargo audit --deny warnings` CI step fails on a clean build due to `paste 1.0.15` unmaintained warning (RUSTSEC-2024-0436)

**Severity:** Minor (CI workflow blocks every merge as-is)
**Confidence:** 100/100
**Principle Violated:** deployment hygiene (a CI gate that always fails is no gate)
**Location:** `.github/workflows/ci.yml:45-46`

#### Description

The new CI workflow includes:

```yaml
- name: cargo audit
  run: cargo audit --deny warnings
```

`cargo audit --deny warnings` exits non-zero when any RUSTSEC advisory at "warning" severity is present. The current dependency graph carries `paste 1.0.15` (transitive via `cosmwasm-crypto` → `ark-ff`), which is classified as unmaintained per RUSTSEC-2024-0436. Reproduced locally:

```
$ cargo audit --deny warnings
Crate:     paste
Version:   1.0.15
Warning:   unmaintained
...
error: 1 denied warning found!
$ echo $?
1
```

The `paste` crate cannot be removed at the verified-rcv layer — it is transitive via `cosmwasm-std 3.0.7`. The fix is either to upgrade `cosmwasm-std` (when an upstream version drops the dependency, which is out of verified-rcv's control), or to explicitly ignore the advisory.

#### Recommended Fix

Either:

**A**: explicit advisory ignore.

```yaml
- name: cargo audit
  run: cargo audit --deny warnings --ignore RUSTSEC-2024-0436
```

with a comment documenting that this is a transitive unmaintained warning out of verified-rcv's control.

**B**: configuration file.

```toml
# .cargo/audit.toml
[advisories]
ignore = ["RUSTSEC-2024-0436"]
```

The configuration-file approach is cleaner because it survives the lifetime of a single CI run. The ignore should be revisited periodically (the upstream may drop the dependency in a future cosmwasm-std bump).

Either fix lets the CI step pass while still alerting on any new advisories that appear.

### Finding N19: `Verify mock-attestation absent from production wasm` CI step false-positive on `verification-key` in an error string

**Severity:** Minor (CI workflow blocks every merge as-is)
**Confidence:** 100/100
**Principle Violated:** deployment hygiene
**Location:** `.github/workflows/ci.yml:58-66`

#### Description

The CI step:

```yaml
- name: Verify mock-attestation absent from production wasm
  run: |
    set -euo pipefail
    WASM="target/wasm32-unknown-unknown/release/verified_rcv_contract.wasm"
    if strings "$WASM" | grep -qE 'mock_attestation|verification\b'; then
      echo "PRODUCTION WASM CONTAINS mock_attestation/verification SYMBOLS — feature flag leak!"
      exit 1
    fi
    echo "OK: production wasm has no mock_attestation/verification symbols."
```

The regex `'mock_attestation|verification\b'` uses `\b` (word boundary) on `verification`. The boundary matches `verification-key` (hyphen counts as a word boundary). The contract's `validate_registry` function returns an error message containing the literal string `"vkey_name must be a non-empty xion.zk-registered verification-key name"`, which is compiled into the production wasm's `.rodata`. Reproduced locally:

```
$ strings target/wasm32-unknown-unknown/release/verified_rcv_contract.wasm \
    | grep -qE 'mock_attestation|verification\b'; echo $?
0
```

The grep matches `verification-key` in the error message. The CI step exits 1 on every PR.

#### Recommended Fix

Narrow the regex to specific symbol patterns that would appear in feature-gated code. CosmWasm Rust feature-gated code typically does not emit feature names directly into `.rodata`; the symbols would appear in mangled function names. A more targeted check:

```bash
# Look for symbols whose mangled name contains the feature path.
if strings "$WASM" | grep -qE '(_mock_attestation_|_verification_|::mock_attestation::|::verification::)'; then
  echo "PRODUCTION WASM CONTAINS mock_attestation/verification SYMBOLS — feature flag leak!"
  exit 1
fi
```

Or use `wasm-objdump` / `wasm-tools` to inspect actual function names rather than `strings`. A function-name-level grep is far less likely to false-positive than a `.rodata` grep.

A simpler interim mitigation: rename the user-facing string "verification-key" to "vkey" or "verifying key" in `validate_registry`'s error message. But this is fragile; another error message in the future could re-trigger the false-positive.

### Finding N20: `cosmwasm-check` CI step fails because the underlying bulk-memory wasm issue is unaddressed

**Severity:** Minor (CI workflow blocks every merge as-is)
**Confidence:** 100/100
**Principle Violated:** deployment hygiene
**Location:** `.github/workflows/ci.yml:52-53`; the root cause is the wasm artifact itself

#### Description

The CI step:

```yaml
- name: cosmwasm-check wasm artifact
  run: cosmwasm-check target/wasm32-unknown-unknown/release/verified_rcv_contract.wasm
```

The release wasm at db2021c and 4cc50b0 fails `cosmwasm-check`'s validator with `bulk memory support is not enabled (at offset 0x6251)`. This finding (`m5` from the original audit) was unaddressed across all four prior cycles and is now caught by the new CI gate — except the gate fails every PR because the underlying issue isn't fixed.

The fix is documented in `docs/deploy.md`'s optimizer-image section and in the original audit's recommended remediation: either use the `cosmwasm/optimizer:0.16.0` Docker image to produce the wasm artifact, or add `.cargo/config.toml` with `target-feature` flags disabling bulk memory.

#### Recommended Fix

Add `.cargo/config.toml`:

```toml
[target.wasm32-unknown-unknown]
rustflags = [
    "-C", "target-feature=-bulk-memory,-multivalue,-sign-ext,-nontrapping-fptoint,-reference-types,-mutable-globals",
]
```

This makes raw `cargo build --release --target wasm32-unknown-unknown` produce a cosmwasm-check-acceptable artifact. The optimizer Docker image is still recommended for size optimization, but the CI gate stops failing.

Alternatively, the CI step could use the optimizer image:

```yaml
- name: Build wasm via cosmwasm/optimizer
  run: |
    docker run --rm -v "$(pwd)":/code \
      --mount type=volume,source=...registry... \
      cosmwasm/optimizer:0.16.0
- name: cosmwasm-check optimized artifact
  run: cosmwasm-check artifacts/verified_rcv_contract.wasm
```

This is more work to set up in CI but matches the prod-deploy path documented in `docs/deploy.md`.

### Finding N21: `HISTORICAL_TALLIES` archives only `TallyResult`, not the `Election` metadata

**Severity:** Informational (consumer can derive partial info from archived tally; some metadata is irrecoverable)
**Confidence:** 85/100
**Principle Violated:** VCL-STMT-004 (incomplete state cleanup is a documentation choice here, not a defect, but worth noting)
**Location:** `crates/contract/src/contract.rs:268-272`, `crates/contract/src/state.rs:156`

#### Description

The N3 closure archives `TALLY_RESULT` into `HISTORICAL_TALLIES: Map<u64, TallyResult>` keyed by `election_id`. It does not archive the `Election` struct itself. After a `CreateElection`-from-`Resolved` transition, the prior election's `title`, `start_at`, `end_at`, and `enclave_pubkey` are silently overwritten by the new election's values.

A consumer who wants to verify "what was the candidate set of election #5?" can recover it from `tally_5.per_round_counts[0]` (each round's candidates are a subset of the original candidates; round 0 has all candidates). A consumer who wants `title` or `start_at` / `end_at` cannot recover those from the archived tally.

For most consumers (vote auditors, downstream contracts referencing the winner), this is fine — the winning candidate set is the load-bearing fact and is preserved. For a fuller archive, the contract would need a second map:

```rust
pub const HISTORICAL_ELECTIONS: Map<u64, Election> = Map::new("historical_elections");
```

The commit message and intent v0.3.10 entry don't acknowledge this gap. Consumers reading the spec text "consumers can pin by election_id and resolve the result indefinitely" may believe more metadata is preserved than actually is.

#### Recommended Fix

Either:

**A**: also archive the Election struct. Add `HISTORICAL_ELECTIONS: Map<u64, Election>` and write to it in the same `Resolved`-branch of `exec_create_election`. Add a `QueryMsg::HistoricalElection { election_id }` query.

**B**: document the partial-archive behavior in `state.rs`'s `HISTORICAL_TALLIES` doc-comment and in the intent.

Option A is more useful but adds storage cost (Election holds candidates + title + timestamps + enclave_pubkey). For verification-of-published-results use cases, option B is sufficient. Pick based on downstream needs.

### Finding N22: Commit-message justification for deferring N13 is incomplete; N2 timelock does not address registration-quote replay against the same registry

**Severity:** Informational (methodology process; N13 itself remains open and possibly underestimated)
**Confidence:** 80/100
**Principle Violated:** N/A (methodology drift)
**Location:** Commit message body of `4cc50b0`; intent.md v0.3.10 entry (implicit)

#### Description

The v0.3.10 commit message's out-of-scope list says:

> Per-election nonce in registration ReportData (would force fresh TDX quote per election; current B8(e) + N2 timelock judged sufficient).

The "N2 timelock judged sufficient" argument is incomplete. N2's timelock blocks registry rotation — i.e., it prevents the admin from swapping `REGISTRY` to point at an attacker-controlled enclave without a public observability window. It does NOT block re-use of an old registration quote against the SAME registry.

Concretely, the N13 attack chain is:

1. A legitimate verified-rcv enclave at time T0 produces a valid `(proof_T0, public_inputs_T0)` for `enclave_pubkey_T0`. The admin uses these for `CreateElection_1`. The registry stays at `R1` throughout.
2. Between T0 and T1, the privkey corresponding to `enclave_pubkey_T0` is exfiltrated by an attacker (TDX side-channel, dstack KMS misconfiguration, insider exfil, etc.).
3. At T1, the operator or an attacker capable of running the legitimate enclave image calls `CreateElection_2` with the SAME `(enclave_pubkey_T0, proof_T0, public_inputs_T0)` triple. The chain verifies the gnark proof again (it still verifies — the proof is good). The measurements still match `R1` (the same registry is in place). The pubkey-binding check passes (`ReportData[0..32] = SHA-256(enclave_pubkey_T0)` is unchanged). `CreateElection_2` succeeds.
4. Voters of election 2 encrypt their ballots under `enclave_pubkey_T0`. The attacker, holding the leaked privkey, decrypts.

The N2 timelock does not touch this chain at all. The registry stays at `R1`; the timelock isn't activated. The replay vector is purely the lack of freshness binding in the registration `ReportData` preimage.

The deferral may be a correct methodology choice (the attack assumes a privkey leak, which is the dstack_kms_trust assumption that the intent already names as operational). But the justification "N2 timelock judged sufficient" is the wrong reason for the deferral — N2 doesn't address this attack at all.

#### Recommended Fix

Either:

**A**: implement the per-election nonce in the registration ReportData preimage as previously recommended (Finding N13 of the prior re-audit). This requires the enclave to produce a fresh TDX quote per election, but the binding cost is one HKDF round per election — negligible compared to the safety gain.

**B**: revise the intent's deferral justification. Acknowledge that N13's residual attack surface (registration quote replay under privkey leak) is operational, not closed by N2. Update the v0.3.10 history entry or add a v0.3.11 PATCH that re-frames the deferral.

The technical concern is real but minor; the methodology drift is the more concerning part. Per the project's "Ask Y" (contract-and-runtime adversarial fan-out) and "Ask Z" (deferred-is-panic), a deferral justification that's incorrect is itself a small process defect.
