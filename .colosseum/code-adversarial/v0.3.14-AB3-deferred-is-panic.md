## Findings (non-panic deferred branches)

### 1. `CandidateNameInvalidUtf8` variant — `#[allow(dead_code)]` claim is honest [Informational]

The variant is declared in `crates/contract/src/error.rs:194` with `#[allow(dead_code)]` and the comment claims it is structurally unreachable because `Vec<String>` is UTF-8 by construction.

Verified: `msg.rs` declares `candidate_names: Vec<String>`; `cw_serde` JSON deserialization fails before the handler is entered on invalid UTF-8 (serde rejects); no Borsh entry path accepts pre-validated raw bytes today. `validate_candidate_names` in `contract.rs:1118` never constructs this variant (grep confirms zero call sites). The claim is honest: the variant cannot fire from the current entry surface. The `#[allow(dead_code)]` is appropriate.

This is NOT a stub-as-Ok finding (the variant isn't a deferred branch in production code, it is an unreachable error case). Recording it here for AB.3 completeness because the intent revision-log entry explicitly flagged it for audit.

Recommended (non-blocking): add a one-line debug_assert / compile-time comment in `validate_candidate_names` explaining the variant is reserved for a hypothetical future Borsh bytes path, OR remove the variant entirely. Current state is defensible.

### 2. Visual-confusability check is non-blocking (intentional) [Clean]

`ui/src/lib/confusables.ts::findConfusablePairs` returns informational pairs. The chain does NOT consult this output. Intent §6.4 explicitly bounds visual confusability as off-chain UX trust. Not a stub.
