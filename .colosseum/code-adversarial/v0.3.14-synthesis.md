## v0.3.14-specific findings actionable now

Documentation across intent + code claimed `verified-rcv:names:v1` was 22 ASCII bytes; actual is 21. Five sites corrected: intent §2.5 + revision-log + contract.rs:85,1103 + attestation.rs:54. Literal byte string unchanged; SHA-256 outputs identical; no test regression.

### B. Intent-doc lag on §2.5 line 204 (AB.1 #3) — FIXED

Publish + registration preimage entries in §2.5 (around line 204) listed v0.3.8 / v0.3.12 forms without the v0.3.14 names_hash addition. The canonical_serialization paragraph at §2.5 line 154 was current; the duplicate descriptions further down were stale. Updated to cumulative v0.3.8 → v0.3.10 → v0.3.11 → v0.3.12 → v0.3.14 trail with explicit names_hash inclusion.

### C. "Writes" vs "mutates" wording in B11 + §6.7 (AB.6 doc-drift) — FIXED

Intent §3.2 B11 row, §6.7 migration discipline section, and v0.3.14 revision-log entry said "no handler writes Election.candidate_names" — but `exec_submit_ballot` does write the whole Election struct back (ballot_count++) with candidate_names preserved byte-identically. The correct invariant is non-mutation, not non-write. Three sites updated; the B11 invariant in code holds either way (sole assigner is exec_create_election).

## v0.3.14-specific findings deferred (defense-in-depth, not blocking)

### D. Registration preimage raw-concatenates enclave_pubkey without length prefix (AB.1 hardening)

`build_registration_report_data` concatenates `enclave_pubkey ‖ Borsh(contract_addr) ‖ u64_LE(election_id) ‖ names_hash`. The `enclave_pubkey` slot is 33 or 65 bytes (secp256k1 compressed or uncompressed) with no length prefix. Disambiguation relies on `validate_enclave_pubkey` enforcing the leading-byte → length invariant (0x02/0x03 → 33B; 0x04 → 65B). The pattern is fragile against future pubkey-type expansion or curve change.

**Status**: NOT a current attack. v0.3.14 doesn't change the pubkey handling (this pattern dates from v0.3.9). Recording as v0.3.15-or-later hardening candidate: prepend `DST_VERIFIED_RCV_REGISTRATION_V1` OR wrap `enclave_pubkey` in `write_borsh_bytes` for length-prefix injectivity.

### E. Registration preimage lacks DST prefix (AB.1 cosmetic)

The v0.3.14 F2 fix added DST tags to `compute_ballots_hash` and `compute_names_hash` preimages. The registration ReportData preimage was not given a similar DST. Defense-in-depth: registration uses DST_TAG[32..64] (a separate purpose tag on the *output* side) which already provides cross-purpose separation, so a missing input-side DST is not a live gap. But the asymmetry with ballots/names internal DSTs is recordable.

**Status**: same as D — recorded for v0.3.15+ hardening. Could land as `DST_VERIFIED_RCV_REGISTRATION_V1` alongside the length-prefix fix.
