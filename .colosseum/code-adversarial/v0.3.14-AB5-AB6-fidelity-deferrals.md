## AB.5 findings (gaps only)

### 1. UI `QueryMsg` union omits `historical_election` variant [cosmetic, not v0.3.14-specific]

- `ui/src/lib/types.ts:118-126` enumerates `config | election | phase | ballots | result | historical_tally | registry | pending_registry`. The contract exposes `QueryMsg::HistoricalElection { election_id }` (msg.rs:170-174, contract.rs:241-243), present since v0.3.12 N21.
- Not introduced by v0.3.14, so strictly out of scope for this pass; flagged as adjacent. Any UI code path that tries to query archived Election metadata will fail typecheck or fall through to an `unknown` cast.
- No security impact (read-only query) and no v0.3.14 field surface affected. Patch is a single union case addition.

Otherwise: every v0.3.14 field surface examined places a value matching the name's implied semantic, and the snake_case wire keys align between contract cw_serde, proto field names, and UI TypeScript types. DST literals are byte-identical across contract and enclave with cross-canonical tests asserting hash-output byte-identity.

## AB.6 findings (weak or refuted deferrals)

### 1. §6.7 prose claim of "no code path other than `exec_create_election` loads + modifies + saves Election" is doc-drift, not a code-side gap [cosmetic]

- Intent §6.7 (intent.md:863) and §8.7 link 7 (intent.md:560) both phrase the B11 structural invariant as "no handler writes the field after CreateElection" / "sole writer of `Election.candidate_names`". `crates/contract/src/contract.rs:401-414` `exec_submit_ballot` does `ELECTION.load → election.ballot_count += 1 → ELECTION.save(&election)`. The save IS a write to the whole Election struct (cw_storage_plus serializes the full value), so the prose claim is technically false even though the `candidate_names` byte payload is preserved.
- The refutable claim "no contract migration path can introduce a name-mutation without a MAJOR-bump audit" stands: there is no `migrate` and no `sudo` entry point in `crates/contract/src/contract.rs` (grep confirms only `instantiate`, `execute`, `query` use `#[cfg_attr(not(feature = "library"), entry_point)]`), no `MigrateMsg` / `SudoMsg` types, and the existing load+modify+save path provably preserves the field byte-for-byte (only `ballot_count` is mutated between load and save).
- Suggested fix: re-word §6.7 to "no handler MUTATES `Election.candidate_names` after CreateElection" rather than "no handler WRITES Election (including round-trips)". The actual property the code provides is non-mutation, not non-write. Severity: cosmetic; B11 holds, the audit-deferral on migration discipline is still justified by the absence of `migrate`/`sudo` entry points and `MigrateMsg`/`SudoMsg` types.

### Per-deferral evidence

**Visual confusability (deferral #1) — justified:**
The chain never compares candidate names to make any decision. Only call sites are: (i) duplicate-detection via byte equality (`==`) at contract.rs:1157; (ii) hash input via `Borsh(name)` at contract.rs:1107 and attestation.rs:113; (iii) storage round-trip via `Election.candidate_names`; (iv) JSON serialization for query responses. No verification function compares names against an external value; no "find candidate by name" lookup exists (lookups are always by `Addr`, e.g. `election.candidates.contains(&info.sender)` at contract.rs:406). A confusable-name attacker cannot trick any chain-side comparison; the trick only succeeds visually on a UI surface, which is precisely the §6.4 off-chain-trust scope.

**F1 registration binding (deferral #2) — justified:**
`build_registration_report_data` (contract.rs:1455-1477) binds `(enclave_pubkey, contract_addr, election_id, names_hash)`. The claim "ballots aren't yet cast at CreateElection time; nothing to bind" is structurally true: `BALLOTS` is empty at CreateElection (post `BALLOTS.remove` loop at contract.rs:362-368), and `election.ballot_count = 0` at line 384. Defense-in-depth still binds `names_hash` so name-tampering is detectable at CreateElection-time. The publish-time leg of the names commitment lives at contract.rs:468 (chain) + attestation.rs:383 (runtime) and is the primary defense; the registration-time leg added in F1 catches the attack one step earlier.

**F3 migration discipline (deferral #3) — justified, modulo doc-drift in finding #1:**
- No `migrate` entry point: confirmed by `grep -E "fn migrate|fn sudo|MigrateMsg|SudoMsg|#\[entry_point\]" crates/contract/src/contract.rs` returning only the three existing `entry_point` macros (instantiate/execute/query at lines 154, 183, 230).
- No `MigrateMsg` / `SudoMsg` types in msg.rs (verified by `grep` in msg.rs returning no hits).
- Future `MigrateMsg` would bypass B11 if it freely loaded + edited + saved Election, which is exactly the §6.7 MAJOR-bump trip-wire. The discipline is correctly stated as a SemVer trip-wire enforced by audit, not by code (consistent with the v0.3.14 intent claim "the lock-flag is theatre, the missing code is the real defense").

**CandidateNameInvalidUtf8 dead-code (deferral #4) — justified:**
All paths that write to `Election.candidate_names` originate from `ExecuteMsg::CreateElection { candidate_names: Vec<String>, ... }` (the JSON cw_serde path: msg.rs:76). `Vec<String>` is type-system-guaranteed valid UTF-8 by Rust's `String` invariant + serde_json's UTF-8-validating deserializer (cw_serde uses serde_json). No `String::from_utf8_unchecked` or `from_utf8` call exists anywhere in `crates/contract/` (grep confirms). The single write at contract.rs:381 inherits valid UTF-8 from the deserialized input. The archival copy at contract.rs:304 preserves the byte payload via cw_storage_plus serialization. The variant is correctly `#[allow(dead_code)]` reserved for a hypothetical future Borsh-bytes path.

**v0.3.14-specific inherited-deferrals check (deferral #5) — justified:**
Reviewed intent.md v0.3.14 entry (line 19) and surrounding context. v0.3.14 introduces six new error variants, two new DSTs, one new B-clause (B11), one new §6.7 subsection, and a strengthened B8(e). All five new symbols have implementation citations in v0.3.14 (compute_names_hash impl + cross-test; validate_candidate_names impl; B11 structural enforcement via grep of `Election.candidate_names` writers; F1 registration extension via build_registration_report_data extension; F2 DST literals + cross-canonical tests; §6.7 contract-migration discipline enforced by absent migrate/sudo handlers). No v0.3.14-specific net-new deferrals beyond those above.
