## Findings (gaps + partials only)

### 1. DST_NAMES documented length off-by-one [LOW — documentation only, no soundness impact]

The intent v0.3.14 §2.5 (line 154) states:
`DST_VERIFIED_RCV_NAMES_V1 = b"verified-rcv:names:v1"` (22 ASCII bytes, same discipline)`

The v0.3.14 changelog entry (line 19) repeats: "22 ASCII bytes".

The code comments at contract.rs:85 and contract.rs:1103 also state "22 ASCII bytes":

```rust
// contract.rs:85
/// v0.3.14 F2 DST prefix for `compute_names_hash` preimage. 22 ASCII
/// bytes. MUST stay byte-identical to the runtime's `attestation::DST_NAMES`.
pub const DST_NAMES: &[u8] = b"verified-rcv:names:v1";
```

`crates/enclave/src/attestation.rs:54` repeats the same "22 ASCII bytes" claim.

Empirical check:
```
$ printf 'verified-rcv:names:v1' | wc -c
21
$ printf 'verified-rcv:names:v1' | hexdump -C
00000000  76 65 72 69 66 69 65 64  2d 72 63 76 3a 6e 61 6d  |verified-rcv:nam|
00000010  65 73 3a 76 31                                    |es:v1|
00000015
```

Manual count: `v(1)e(2)r(3)i(4)f(5)i(6)e(7)d(8)-(9)r(10)c(11)v(12):(13)n(14)a(15)m(16)e(17)s(18):(19)v(20)1(21)` = **21 bytes**.

Comparison with the ballots DST: `verified-rcv:ballots:v1` is 23 bytes (correctly stated). The difference between `names` (5 chars) and `ballots` (7 chars) is 2, so 23-2 = 21, confirming names is 21.

**Soundness impact**: zero. The byte-string LITERAL in code is the source of truth for the hash preimage; SHA-256 doesn't read the documented length. The contract-side and enclave-side constants are byte-identical (both `b"verified-rcv:names:v1"`), so the cross-canonical byte-identity test still passes.

**Methodology impact**: AB.2 byte-exact discharge requires the spec's stated length to match reality. A future change attempting to "fix" the literal to be 22 bytes (e.g., `verified-rcv:names:v1\0`, or `verified-rcv:names:v01`) by trusting the intent's claim would silently break byte-identity with deployed deployments. The intent's arithmetic is the authoritative spec; the literal is the artifact. They must agree.

**Fix**: patch intent v0.3.14 §2.5 (line 154) and the v0.3.14 changelog entry (line 19) to state "21 ASCII bytes" for `DST_VERIFIED_RCV_NAMES_V1`. Also patch the code comments at `crates/contract/src/contract.rs:85` (around the `DST_NAMES` constant), `crates/contract/src/contract.rs:1103` (inside `compute_names_hash`), `crates/enclave/src/attestation.rs:54`, and `crates/enclave/src/attestation.rs:110` from "22 ASCII bytes" to "21 ASCII bytes". The fix is purely documentary; no hash preimage changes, no test changes, no cross-canonical test change. PATCH-level intent bump (no symbol change, no invariant change, only arithmetic typo). This is exactly the kind of low-severity but methodology-load-bearing discrepancy AB.2 is designed to surface; leaving it in place erodes the byte-for-byte discharge claim that anchors the trust chain.
