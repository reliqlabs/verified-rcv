# AB.4 who-controls — v0.3.14 implementation

Lens AB.4 (code-adversarial): name the supplier of every stored field and
the validation site that constrains it; flag any field whose supplier is
not the chain/enclave and whose validation is missing, lenient, or
bypassable. Scope = v0.3.14-touched surfaces (the `candidate_names`
addition + everything that hashes or transports it).

## Findings

### 1. `Election.title` has no chain-side validation [cosmetic, pre-existing — not v0.3.14]
- Supplier: admin via `ExecuteMsg::CreateElection { title, ... }` (`msg.rs:70`).
- Storage write: `contract.rs:379` — verbatim copy from the message.
- No length cap, no NUL filter, no control-character filter.
- Impact: an admin can store a 1-MB title or one with embedded NUL/CR/LF, which JS/log consumers may render unsafely. This is gas-paying and admin-only, so it's not a security issue, but the title is the second admin-supplied display string on `Election` and now sits alongside `candidate_names` whose validation is rigorous. The asymmetry is worth a one-line cap.
- Not in scope for v0.3.14 to fix, but flagging because the AB.4 enumeration surfaced it.

### 2. `candidate_names` validation runs AFTER candidate-distinctness, BEFORE timestamps [informational]
- Order at `contract.rs:309-328`: candidates non-empty → candidates distinct → **candidate_names parallel-validate** → start_at/end_at sane → enclave_pubkey shape → registration quote.
- A submission with bad `candidate_names` AND bad timestamps surfaces the `CandidateName*` error first.
- Not a gap — error ordering is consistent and each error variant is specific (per `error.rs:174-208`).

### 3. Server side does not pre-validate `candidate_names` before hashing [verified safe]
- `server.rs:76-83,165-173`: both RPC handlers destructure `candidate_names` and pass it straight into `produce_*_artifacts`. The enclave acts as a hash oracle.
- Safety derives entirely from the chain re-validating + recomputing the hash before binding. The publish-time commit-hash mismatch (`AttestationCommitMismatch`) catches divergence at `contract.rs:483`; the registration-time `verify_registration_quote` catches it at `contract.rs:351-360`.
- The chain validation runs at `contract.rs:321` BEFORE the registration check at `contract.rs:351`, so a host that submits a malformed list (e.g. with a NUL byte) hits `CandidateNameContainsNul` rather than `AttestationCommitMismatch`. That's the correct precedence — the more-specific error fires first.
- No code-level gap. The cross-layer design is sound.

### 4. `DST_NAMES` and `DST_BALLOTS` are different lengths but neither carries an internal length prefix [informational]
- `DST_BALLOTS = b"verified-rcv:ballots:v1"` (23 bytes), `DST_NAMES = b"verified-rcv:names:v1"` (22 bytes). Both at `contract.rs:84,87`.
- Comments at `contract.rs:78-83` argue these prefixes are "structurally inseparable from the rest of the preimage". Since the two preimages have different first bytes (`...ballots...` vs `...names...`) at position 13, no collision on the leading bytes is reachable for any input. The differing total preamble length plus a u32_LE count prefix means the hash inputs cannot be equal for any (names_list, ballots_list) pair.
- Verified safe; no gap.

### 5. Client-side `validateCandidateNames` is a strict subset of chain validation [verified, no drift]
- `ui/src/lib/format.ts:55-65` (single-name): byte-length via `TextEncoder` (UTF-8), >=1, <=64, no ` `.
- Chain at `contract.rs:1134-1152`: byte-length via `as_bytes().len()`, >=1, <=64, no `0x00`.
- Threshold constants match (64 in both; `format.ts:45` vs `contract.rs:101`).
- Duplicate scan: client uses `Map<string, number>`; chain uses O(n²) byte-equality. Both case-sensitive byte-equality. Equivalent under JS string equality (which is UTF-16 code-unit equality but maps 1:1 to UTF-8 byte-equality given equal UTF-8 encodings).
- No client-side check is stricter than chain (which would allow chain-valid inputs the UI rejects). No chain check is stricter than client (which would surface as a round-trip surprise).
- Verified: any client-form-passing submission is chain-accepted; any client-rejected submission would also be chain-rejected.

### 6. `CandidateNameInvalidUtf8` is dead-code-reachable only via a future Borsh path [informational]
- `error.rs:193-195` marks the variant `#[allow(dead_code)]`. Comment at `state.rs:81` and `error.rs:189-192` notes it's reserved for a future Borsh bytes ingress that could carry pre-validated raw bytes.
- Current ingress: `cw_serde` JSON deserialization of `Vec<String>`, which is type-system-guaranteed valid UTF-8.
- No bypass path: there is no alternate execute-msg encoding that accepts raw bytes for candidate names today. Verified by inspecting `ExecuteMsg::CreateElection` field types at `msg.rs:69-86` (all `String` / `Addr` / `Timestamp` / `HexBinary` — none route to a raw `Vec<u8>` for names).

### 7. No migrate / sudo / reply handler [verified, matches intent §6.7]
- `grep "fn migrate\|MigrateMsg\|sudo\|reply" crates/contract/src/` returns no matches.
- The only entry points are `instantiate`, `execute`, and `query` (at `contract.rs:155, 184, 231`).
- Conclusion: no validation-bypass path via migration. Intent v0.3.14 §6.7 holds in code.

## Summary

- Critical: 0
- Serious: 0
- Cosmetic: 3 (G1 `title` cap missing, G2 candidates.len() no upper bound, G3 ciphertext byte cap missing — all pre-existing, none v0.3.14-introduced)
- Informational / verified-safe: 4 (F1 server hash-oracle pattern, F2 publish-commit recheck, F3 client/chain validation parity, F4 DST collision impossibility)

**v0.3.14-introduced state (`Election.candidate_names`) has tight chain-side validation, no bypass path, and a defense-in-depth cross-layer binding via `names_hash` in both the registration and publish quotes. AB.4 finds no v0.3.14 who-controls regression.**

The three cosmetic findings are pre-existing patterns the v0.3.14 work makes more visible by contrast (admin-supplied `candidate_names` is now strictly validated while sibling admin-supplied fields `title` and `candidates.len()` remain unbounded). They are out of scope for v0.3.14 to fix but should be noted on the v0.4 ask list as candidates for a small "tighten admin-supplied display fields" follow-up.
