## Findings

### 1. enclave_pubkey concatenated without length prefix in registration ReportData preimage [hardening]

- **Category**: commitment-coverage gap (fragile concatenation; relies on out-of-band length invariant)
- **Affected**: `crates/contract/src/contract.rs:1461-1465`; `crates/enclave/src/attestation.rs:268-273`
- **What's wrong**: The registration ReportData preimage starts with raw `enclave_pubkey` bytes (33 or 65 bytes) immediately followed by `borsh_string(contract_addr)`. There is no length prefix on the pubkey itself. Unambiguity of the concatenation depends entirely on the chain-side `validate_enclave_pubkey` invariant that leading byte determines length (0x02/0x03 → 33 bytes, 0x04 → 65 bytes). If that validator is ever weakened (e.g., to accept hybrid keys, or to add a future Ed25519 variant), the preimage encoding silently becomes ambiguous: an attacker could find `(pk_a, addr_a)` and `(pk_b, addr_b)` such that `pk_a ‖ borsh(addr_a) = pk_b ‖ borsh(addr_b)` byte-for-byte, allowing one registration quote to be replayed against a different `(pk, addr)` pair. The defense is implicit (validator coincidence) rather than encoded in the preimage. Compare with `ballots_hash` and `names_hash`, both of which DO carry an explicit u32-LE count prefix as part of their domain-separation discipline.
- **Cite**:
```rust
// contract.rs:1461-1469
let mut preimage =
    Vec::with_capacity(enclave_pubkey.len() + contract_addr.len() + 16 + 32);
preimage.extend_from_slice(enclave_pubkey);          // <-- raw, no length prefix
write_borsh_string(&mut preimage, contract_addr);
preimage.extend_from_slice(&election_id.to_le_bytes());
preimage.extend_from_slice(names_hash);
```
- **Fix**: Add a 4-byte u32-LE length prefix on `enclave_pubkey` (`write_borsh_bytes(&mut preimage, enclave_pubkey)` instead of raw `extend_from_slice`). This also matches the discipline used for `ballots_hash`'s body entries. Add a cross-test asserting that swapping pubkey length while padding `contract_addr` to compensate produces a distinct hash. Alternatively, prepend a DST tag (`b"verified-rcv:registration:v1"`) for consistency with the v0.3.14 F2 DST-prefix discipline applied to `ballots_hash` and `names_hash`. Either fix removes the dependency on `validate_enclave_pubkey`'s leading-byte invariant for preimage unambiguity.

### 2. Registration ReportData preimage has no DST prefix, unlike ballots_hash and names_hash [cosmetic]

- **Category**: commitment-coverage discipline asymmetry
- **Affected**: `crates/contract/src/contract.rs:1455-1477`; `crates/enclave/src/attestation.rs:256-281`
- **What's wrong**: v0.3.14 F2 added DST prefixes to `compute_ballots_hash` (`DST_BALLOTS = b"verified-rcv:ballots:v1"`) and `compute_names_hash` (`DST_NAMES = b"verified-rcv:names:v1"`) preimages explicitly to prevent cross-hash substitution. The same discipline is not applied to the registration ReportData preimage (which is also a SHA-256 over a structured concatenation). Cross-purpose substitution between publish ReportData[0..32] (preimage starts with `borsh_string(contract_addr)` → first 4 bytes are u32-LE length ~40-50) and registration ReportData[0..32] (preimage starts with raw pubkey → first byte 0x02/0x03/0x04) is in practice distinguishable by leading byte. But: a future revision that changes `contract_addr` field shape, or adds an Ed25519 pubkey variant, could remove that practical distinguisher. The DST_TAG[32..64] half does enforce purpose separation at the consumer (`check_dst_tag`), but a DST on the **preimage** itself would harden the SHA-256 input against future encoding shifts.
- **Cite**: same lines as Finding 1; no DST_REGISTRATION constant exists in either file.
- **Fix**: For consistency with the v0.3.14 F2 ballots/names discipline, add `DST_REGISTRATION = b"verified-rcv:registration:v1"` as a preimage prefix in both `build_registration_report_data` impls. Mirror the cross-test that verifies the contract and runtime preimages are byte-identical. This is cosmetic-tier because the consumer-side DST_TAG[32..64] check already provides purpose separation; the preimage DST is defense-in-depth.

### 3. Intent §2.5 line 204 and §3.2 B8(c) discharge row 535 specify stale preimage shapes [no impl gap — flag for intent doc patch]

- **Category**: intent-doc lag, not commitment-coverage gap
- **Affected**: `.colosseum/intent.md:204` (publish preimage) and `.colosseum/intent.md:535,543` (B8(c) and B8(e) rows)
- **What's wrong**: Intent §2.5 line 204 says publish `data = SHA-256(canonical_serialization(contract_addr ‖ chain_id ‖ election_id ‖ ballots_hash ‖ tally_body))` — missing `names_hash`. The §3.2 B8(e) row at line 543 says registration preimage is `SHA-256(enclave_pubkey ‖ Borsh(contract_addr) ‖ u64_LE(election_id))` — missing `names_hash`. The v0.3.14 entry at intent line 19 and the canonical_serialization paragraph at line 154 DO include `names_hash`. The implementation in both files correctly includes `names_hash`, so this is an intent-doc consistency issue, not a code finding. The impl is the v0.3.14 form; the §2.5 line 204 and §3.2 B8(c)/(e) rows lag.
- **Cite**: intent.md line 204 vs intent.md line 154 disagreement; contract.rs:1039-1057 (`compute_commit_hash`) and contract.rs:1455-1477 (`build_registration_report_data`) implement the line-154 form.
- **Fix**: Patch intent.md §2.5 line 204 to read `… ballots_hash ‖ names_hash ‖ tally_body))`, and patch the §3.2 B8(e) discharge row (line 543) to reflect the v0.3.14 F1 four-field preimage. This is not a v0.3.14 commitment-coverage gap, but it weakens the §3.2 → code citation chain that AB.1 is supposed to check.

## Methodology notes

- All findings cite specific code lines; no speculative gaps.
- The two hardening/cosmetic items concern the registration ReportData preimage's asymmetric discipline relative to v0.3.14 F2's ballots/names preimage DST + length-prefix treatment. The impl is currently correct under the implicit invariants of `validate_enclave_pubkey` and the §2.5 ReportData DST_TAG[32..64] enforcement; the asymmetry is a regression-risk surface for future revisions, not an active vulnerability.
- Finding 3 is an intent-doc patch ask (the §2.5 line 204 narrative was not updated for v0.3.14, while the canonical_serialization paragraph at line 154 was). The code matches line 154's form, so per the user's "intent doc is the source of truth" policy, intent line 204 should be patched to line 154's form rather than the impl being changed.
