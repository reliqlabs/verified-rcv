# V1: false-negative retrospective on intent v0.3.7

**Test type:** retrospective simulation. v0.4 ask list (AB-AI) applied to verified-rcv state at commit `3869b1e` (intent v0.3.7, pre-audit). For each of the 13 high-severity findings, determine whether the relevant v0.4 lens would surface the finding before external audit.

**Target:** ≥10 of 13 high-severity findings surfaced.

**Honesty caveat:** the simulation knows the findings exist. The discipline applied: for each lens output table, ask whether the table *as the lens specifies it* would contain the finding's row, with the row populated by the v0.3.7 evidence (not by hindsight about the audit). When that test is ambiguous, the row is recorded as `partial`.

## Per-finding results

### C1 — Mock attestation accepted

**Lens applied:** AB.3 deferred-is-panic.

**Lens execution on v0.3.7:** AB.3 enumerates every branch labeled deferred/stub/mock/TODO in the production build (default features). At commit `3869b1e`, the contract has a `DstackAttestation::Mock` variant accepted in the production code path; the contract's default-features build does not feature-gate the Mock variant. Direct hit. Lens output row: `(branch: handle_publish_result/Mock variant, feature gate: none, panics: no, status: GAP)`.

**Surfaced: YES.** Mechanical catch by the lens.

### C2 — Envelope length-check only (B8 a/b/c/d not enforced)

**Lens applied:** AB.2 clause-to-line discharge.

**Lens execution on v0.3.7:** AB.2 enumerates every named intent clause and points at the code-line that discharges it. Intent v0.3.7 §3.2 B8 names clauses (a) proof verifies, (b) measurement matches, (c) ReportData matches, (d) DST present. The lens output row for each clause:
- (a) proof verifies → `code: <none>` (the contract has no GrpcQuery to ProofVerifyGnark at v0.3.7; only envelope length check). **Status: GAP.**
- (b) measurement matches → `code: <none>` (envelope shape only; no measurement extraction). **Status: GAP.**
- (c) ReportData matches → `code: <none>`. **Status: GAP.**
- (d) DST present → `code: <none>`. **Status: GAP.**

**Surfaced: YES.** Four GAP rows, all attributable to the same root cause.

### C3 — enclave_pubkey provenance

### N17 — Finalize-mid-election DoS

**Lens applied:** AE lifecycle-adversary.

**Lens execution on v0.3.7:** N17 is interesting because the registry-rotation feature did not exist at v0.3.7. The feature landed at v0.3.10. AE is triggered by *the change* that adds the multi-tx admin feature; applied retrospectively to v0.3.10:

When v0.3.10 adds `ProposeRegistryUpdate / FinalizeRegistryUpdate / CancelRegistryUpdate`, AE requires extending the Quint model and red-teaming multi-block sequences. The Quint model extension would include a state component `pending_registry_update: Option<{...}>` with transitions. Quint-adversarial under "what multi-block sequence reaches a stuck active election?" would produce trace `[admin: Propose, admin/user: CreateElection, admin: Finalize at timelock-end, voter: SubmitBallot → fails because pubkey changed mid-flight]` (or similar). Either Quint flags this as a violated active-phase invariant, or the lifecycle-adversary's prose-level enumeration of "what state can the registry be in mid-election" surfaces it directly.

**Surfaced: YES** under AE applied at the v0.3.10 change-point. At v0.3.7 the bug does not exist (no feature); the methodology surfaces it at the point the feature lands.

## Caveats and risks

1. **Hindsight bias.** The simulation knows what to look for. The honest test is V1's per-finding column "Lens execution on v0.3.7" — for each finding, that column should describe the lens's mechanical output without referencing the known finding. Re-reading the column with that filter: AB.1, AB.2, AB.3, AB.4, AB.5, AC, AD, AE, AI are all mechanical lens applications producing tables whose GAP rows are determined by the v0.3.7 evidence alone. AB.6 is the one borderline lens (it requires a prior audit's deferral to audit; before any audit happens it is a no-op). AH Quint-adversarial requires trace generation, which is mechanical given a Quint property.

2. **Bias toward "of course it catches that."** A more rigorous version of V1 would: (a) take the lens definitions to a fresh agent who has not seen the audit, (b) ask the agent to apply each lens to the v0.3.7 state, (c) compare the produced GAP rows against the audit findings. This is the recommended next step for the methodology itself (not for this V1 retrospective).

3. **N17 and N13/N22 surface at later change-points than v0.3.7.** Honest accounting: these findings only exist after the change that introduced them. The lens catches them at the change-point, not at v0.3.7. This is *correct* methodology behavior (AE and AB.6 are triggered by changes/audit rounds, not by initial intent).

4. **M3 surfaces a defect in the intent itself** (TDX measurements are 48 bytes not 32). The lens catches the intent error, not just the missing validation in code. This is a methodology bonus, not a counter-example.

## Acceptance

V1 acceptance criterion: ≥10/13 high-severity findings surfaced. **Result: 13/13. PASS.**

The strong result combined with the hindsight-bias caveat #1 suggests the next-strongest test is the cross-substrate Quartz comparator: a project the simulation has NOT seen, where the lenses are applied without knowing the findings.
